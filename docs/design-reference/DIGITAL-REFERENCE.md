# Digital Theme — Approved Design Reference

Reference file: `digital.html`

## Theme identity

Digital is the most expressive launch mode.

The approved reference establishes an atmospheric, cybernetic/digital-studio language using:

- deep navy/near-black space;
- luminous cyan;
- secondary emerald and amber accents;
- layered transparent surfaces;
- glows;
- grid overlays;
- HUD labels;
- large bold typography;
- technical mono metadata;
- responsive project cards;
- status chips;
- spatial telemetry motifs.

The intended reaction is:

> **An expressive interactive digital studio with strong systems/technology character.**

This is not the same theme as Engineer.

Engineer is precise and utilitarian.

Digital is atmospheric and expressive.

## Background

The reference combines:

- near-black base;
- 40px grid;
- large blurred ambient color fields;
- occasional dot matrix;
- transparent surfaces;
- atmospheric depth.

This layering is central to Digital.

Do not flatten it into a normal dark SaaS page.

## Header

Reference:

- sticky;
- translucent dark surface;
- cyan border;
- two-line brand;
- Japanese name line;
- `// WORK` style desktop nav;
- language pill;
- explicit Digital mode indicator;
- mobile drawer.

The header feels like a HUD but still behaves like familiar navigation.

Preserve that balance.

Characteristics:

## Work section

The approved reference uses three major system cards in a desktop grid.

This is an important update to earlier speculative Digital planning.

For the homepage baseline, preserve the reviewed reference unless later revised.

### Card characteristics

- one card per flagship project;
- translucent dark surface;
- theme-colored border;
- theme-colored glow on hover;
- compact system title bar;
- embedded application preview;
- project title/category;
- concise description;
- stack/meta;
- technical CTA.

Theme accent may vary by project:

- cyan;
- emerald;
- amber.

### Shared architecture rule

These are not Digital-only project objects.

They consume the same project data as Editorial and Engineer.

The Digital renderer may choose a project-specific accent based on semantic data or curated presentation metadata if needed.

Do not hardcode factual project differences here.

## About / bridge section

Reference turns About into a spatial systems narrative.

Desktop:

```text
Narrative:
6 columns

Connection visualization:
6 columns
```

This is a strong Digital interpretation.

Preserve the concept:

> identity/background is represented as a connected system rather than an editorial biography.

### Critical factual warning

The reference contains generated statements about personal background, roots, language, destination, and relocation.

Do not use those statements unless independently present in real portfolio content.

The visual bridge motif may remain while factual text is replaced.

## Capabilities

Reference uses three large translucent panels.

This is a useful Digital arrangement.

Actual categories and technology lists should be sourced from real registries.

Do not inherit prototype claims automatically.

## Lab

Reference uses four technical prototype cards.

Visual pattern:

- compact;
- dark;
- theme-colored hover border;
- graphic/code-like preview;
- experiment title;
- mono technical description.

This is suitable for Digital Lab previews.

Experiment names/content are placeholders.

## Contact

Reference uses:

- centered layout;
- availability/status pill;
- huge bold CTA;
- technical subcopy;
- bright primary action;
- secondary GitHub action.

Production should retain the bold Digital closure while replacing generated availability/contact claims.

## Footer

Reference uses:

- dark technical footer;
- two-row structure;
- identity/social navigation;
- telemetry/copyright row.

Decorative coordinates/system version should not become factual claims unless intentionally defined.

## Geometry

Digital uses:

- rounded-lg/xl surfaces;
- pills;
- glowing border states;
- more depth than Engineer;
- layered transparent panels.

This distinguishes it from Engineer's square technical geometry.

## Glow discipline

Glow is an accent, not a blanket effect.

Use it primarily on:

- active mode;
- selected/hovered project;
- major CTA;
- focused visual node;
- system status.

Avoid glowing every border and every line.

## Accent semantics

Reference suggests:

- cyan = primary identity/interaction;
- emerald = positive/backend/system accent;
- amber = secondary project/planning accent;
- indigo = spatial/depth supporting accent.

Maintain coherent semantics.

## Motion

Digital has the strongest motion allowance.

Potential:

- subtle pulses;
- glow intensity transitions;
- media continuity;
- ambient background drift;
- project-card response;
- diagram/node animation;
- pointer-responsive hero enhancement.

Do not add scroll hijacking.

Reduced motion must remain polished.

## Advanced effects

The reference does not require WebGL.

Digital is already visually distinct through:

- typography;
- surfaces;
- grid;
- glow;
- composition;
- status language.

Therefore:

> Do not add heavy WebGL merely to make Digital feel advanced.

Use it only when an effect meaningfully improves the experience.

## Mobile identity

Retain:

- cyan/dark palette;
- bold display type;
- HUD controls;
- layered surfaces;
- project accent borders;
- technical mono labels.

Reduce:

- ambient background cost;
- overlapping spatial composition;
- long telemetry strings;
- nonessential motion.

A Digital case study may use:

- interactive architecture;
- visual sequences;
- strong transition continuity.

But it must still read as a normal accessible document when linearized.

## Prototype content that must not be trusted

The Digital reference contains especially extensive generated content.

Do not automatically use:

- generated professional titles;
- project metrics;
- uptime/latency values;
- project technology stacks;
- database/API technology claims;
- alternate Hospitality project naming;
- Tokyo as required destination;
- personal roots/identity wording;
- bilingual/cultural identity claims;
- relocation-readiness claims;
- invented Lab experiments;
- older accessibility-standard wording;
- AWS service lists;
- email/social URLs;
- generated status/version labels.

The real content system decides what is true.

The prototype decides how Digital can present that truth.
