## Security evidence for the case study

Use one semantic technical section, **`technical-security`**, titled **“Protecting account-owned travel plans.”** Its visible summary should explain that authentication identifies the user, service checks bind resources to that user, CSRF protects cookie-authenticated mutations, and login limiting constrains repeated failures. Present the controls together with the limits below. This inspection is source review and existing-test verification; it is not a penetration test or completed security audit.

Paths in the table are repository relative. Java classes are under `backend/src/main/java/com/japantravelplanner/`; corresponding Java tests are under `backend/src/test/java/com/japantravelplanner/`.

| Control / threat or failure | Mechanism and exact evidence | Existing tests and limits |
| --- | --- | --- |
| **Credentials and session lifecycle:** prevent unauthenticated private operations and end the current login on logout. | `controller/AuthController.java:56-98`, `login`, authenticates with `AuthenticationManager`, creates a `SecurityContext`, and stores it as `SPRING_SECURITY_CONTEXT` in `getSession(true)`. `config/SecurityConfig.java`, `authenticationProvider`, uses DAO user details. `controller/AuthController.java:124-131`, `logout`, invokes `SecurityContextLogoutHandler`; account deletion does likewise (`AccountController.deleteAccount`). | No AuthController or filter-chain tests exist. The custom login does not explicitly call `changeSessionId` or a `SessionAuthenticationStrategy`; session-ID rotation and CSRF-token rotation on login are **not established** by this path or tests. Password change does not explicitly invalidate other sessions. Avoid claiming verified session-fixation prevention or all-device logout. |
| **Password hashing and sensitive account changes:** avoid storing plaintext passwords and require the current password for destructive changes. | `config/SecurityConfig.java:78-80`, `passwordEncoder`, returns BCrypt. `service/UserService.java:38`, `registerUser`, encodes before storage; `changePassword` re-encodes; `getVerifiedUser:60-66` checks the current password; `CustomUserDetailsService.loadUserByUsername` supplies the stored hash to Spring. | `UserServiceTest` covers registration, duplicate rejection, successful verified password change and owned-data deletion order. Encoder is mocked; tests do not prove real BCrypt behavior or rejection of a wrong current password. | **CSRF:** prevent an unrelated site from issuing accepted cookie-authenticated mutations. | `frontend/src/api/api.js:67-94`, `getCsrfToken`/`csrfFetch`, gets `/api/auth/csrf` with credentials and attaches the returned header/token to mutation requests. `AuthController.getCsrfToken` returns token/header name. `SecurityConfig.securityFilterChain:37-41` enables cookie-backed CSRF with a request attribute handler; `csrfTokenRepository:132-143` configures SameSite and Secure. No explicit CSRF ignore routes are configured. | `frontend/src/api/api.test.js`, “uses CSRF protection when creating a trip from a template,” verifies the request header and credentials against mocked fetch. No existing backend test sends missing/invalid CSRF through Spring's filter chain. CSRF cookie is deliberately readable by JavaScript (`withHttpOnlyFalse`); session cookie is configured HttpOnly. This is not an XSS defense. |
| **Resource ownership:** prevent a user from selecting another account's trip/item/template ID. | Controllers derive username from server `Authentication`, not an owner field supplied by the client. `TripService.getTripById:38` and update/delete/duplicate use `findByIdAndUser_Username`. `TripItemService.updateActivity:210-223` first resolves the owned trip, then checks that the item belongs to it; analogous checks exist for other types/deletion. `SavedItineraryItemService.saveFromTrip:49-53` checks item-to-trip membership and `getOwnedSavedItem:108` uses owner-scoped lookup. `TripTemplateService.getAccessibleTemplate:117-125` permits public templates or matching private owners. | `TripTemplateServiceTest.instantiateHidesAnotherUsersPrivateTemplate` asserts rejection and no trip save; `SavedItineraryItemServiceTest.deleteDoesNotExposeAnotherUsersSavedItem` asserts rejection when scoped lookup is empty. These are mocked service tests. `TripServiceTest` covers owned success, not cross-account rejection; no HTTP/database ownership matrix exists. |
| **Public versus private boundary:** allow anonymous browsing while restricting personal plans. | `SecurityConfig.java:44-63`: GET public-template routes and health are public; login/register/CSRF initialization are public; `/api/account/**`, `/api/trips/**`, `/api/templates/**` and `/api/library-items/**` otherwise require authentication. No existing security-chain test checks unauthenticated private access. `.anyRequest().permitAll()` is the fallback; future API namespaces must be added deliberately to the protected matchers. UI route guards are convenience, not the server security boundary. |
| **Input and domain validation:** reject malformed or inconsistent plans before saving. | Controllers use `@Valid`; `dto/RegisterRequest`, `TripRequest`, activity/lodging/transport DTOs constrain required values and lengths. `TripService.createTrip` checks trip date order. `TripItemService.validateDateWithinTrip:392`, `validateActivity`, `validateTransportation`, `validateLodging` and `validateCost:483` enforce trip/date/time/cost rules. | `TripServiceTest.createTripRejectsEndDateBeforeStartDate`, `TripItemServiceTest.createActivityRejectsDateOutsideTripDates`, and `GlobalExceptionHandlerTest.returnsStableFieldCodesForValidationErrors` cover specific service/handler cases. No request-validation integration test exercises all annotations. `ChangePasswordRequest.newPassword` has `@Size` but no required-value annotation: the DTO does not establish null rejection; whitespace-only values also lack a blank-value rule. |
| **Login limiting:** constrain repeated failed guesses per username and client IP. | `AuthController.login:61-79` uses `getRemoteAddr`, checks limits, records authentication failures, then checks again; success clears username failures, leaving IP failures. `LoginAttemptService.checkAllowed`, `recordFailure`, `buildCache` and `AttemptWindow` use bounded Caffeine caches and synchronized timestamp deques. | **Client-IP/proxy trust:** make IP limits apply to the intended client boundary. | Login uses servlet `getRemoteAddr`; it does not parse arbitrary forwarding headers itself. `application.properties:30-31` defaults forwarding to `NONE`. `docs/DEPLOYMENT.md` recommends `FRAMEWORK` behind Railway. | Actual environment and trusted-proxy chain were not inspected. The single-origin topology reduces CORS setup; CORS does not replace authentication or CSRF. Seven days is a configured inactivity timeout, not a verified absolute session lifetime. |
| **Secrets and error handling:** avoid credentials in project copy and avoid leaking account/exception details in normal error paths. | Database values come from environment placeholders (`application.properties:3-5`); `.gitignore` excludes local `.env` files. `GlobalExceptionHandler` maps domain/validation/auth errors to stable codes; bad credentials get a common message; unavailable owned resources use controlled errors. No generic unexpected-error disclosure test, secret-history audit or live configuration review was performed. Stable error codes help localization, but do not prove every failure is sanitized. |
